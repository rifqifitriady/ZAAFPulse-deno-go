# P4e results: guardrails and the budget guard on the go engine (slices S6 and S7)

Date: 2026-11-16. Branch `migrate/p4e-guard-wire`, cut from `migrate/deno-go` at `ae7b9ab` (P4c merged). Spec
the p4e-guard-wire design, plan the p4e-guard-wire plan
(Decisions 1–25; owner answers of 2026-11-16 recorded as Decisions 26–29).

## What ships

- **Guardrails on the go path (S6).** OpenAI-format chat calls, whole and streamed, that a guardrail check applies to
  are served by the go engine: `gw/guard.CheckBody` runs on proxyChat's upstream body (the client body with the stream
  usage merge), after the rate limit and the budget, before the provider. Redaction goes upstream; the outcome goes in
  the usage line; a block is the JS 400 `guardrail_blocked`, any other failure of the checks the JS 500
  `guardrails failed` (fail closed), each with the JS line. A refused stream gets the JSON answer. No check on model
  output (owner answer: input only, as JS). Policy: the pushed `gateway.guardrails` with the key's own modes.
  `guard.Prepare()` runs at gateway start in a goroutine.
- **Budgets on the go path (S7).** The JS price rule (a limited key needs a priced or private model, else 402), then
  `ipc.Decide` on the newest snapshot (402 with the budget's name, no line), then the engine's own spend not yet in that
  snapshot, so the call after the one that used a budget up is refused at once, as in JS. A stale snapshot (over
  `--stale-ms`, 5 s) or none lets metered calls through, each line marked `budget: "unchecked"`; the supervisor counts
  and alerts as before. A budget the snapshot shows exceeded is refused even when stale.
- **The request path never waits for the control plane.** Usage lines are stored in the outbox and handed to one sender
  goroutine (memory queue of 4,096 lines, then reads from the outbox), in seq order, once.
- **A key or budget change is in force before its save answers.** A reload sends the budget snapshot first; a budget or
  cost-settings save in the cost API reloads the gateway and waits for it (`front.synced`).
- **Shadow.** Guarded calls are compared by the provider body and `usage.guard`; refusals (400, 500, 402) by status, the
  error body and the refusal's line (the JS capture now keeps both); a budget disagreement is `skipped` as the
  snapshot's lag.
- **Hand-offs removed:** key budget, stale snapshot, blocking budget, guardrails. Kept: access, method, key, body, model,
  provider format (P4d), OAuth2/service account (P4g), credential, token saver with tool results, `stream_options` shape.

### Heap and GC of a guarded 20 MB call (Task 7, owner answer 27)

`TestGuardedBigBody`, M-series Mac, `PlanChat` + `Guard`, default policy (secrets redact, injection log), one user message
of the guard corpus, three runs:

| Soft memory limit | Peak extra heap | GCs during the call | Wall |
|---|---|---|---|
| none | 218–289 MB | 6–8 | 0.50 s |
| 64 MiB (the default) | 63–88 MB | 452–469 | 0.56–0.58 s |
| 128 MiB | 63 MB | 463–467 | 0.56–0.57 s |
| 256 MiB | 122 MB | 3 | 0.44–0.45 s |

An adversarial 20 MB body (all three checks on) is refused by its step budget (`overrun "pii"`) in 1.37 s, 122–162 MB.

The gateway does go into constant GC on such a call under the 64 MiB default: about 460 collections in half a second,
about +15% wall time, and the heap is held to the limit rather than past it (the limit is soft, so nothing fails). The
numbers are from the test process, whose own baseline heap is larger than the idle gateway's, which is why 128 MiB
behaves like 64 here; they are an upper bound on what the gateway needs, not a measure of its RSS. The thrash grows with
the number of large guarded calls at once (Decision 23 sets no concurrency limit); Go's GC CPU cap keeps that slow, not
failing. **Recommendation:** keep 64 MiB as the default for typical traffic (small bodies; M4's 69 MB at 500 streams),
and for owners who send multi-megabyte prompts through guarded keys document `gateway.memLimitMB` up to 256 as a
conservative upper bound (the guard's own bound per 20 MB call), to be refined by measuring the gateway's RSS at the
final step. Not changed in P4e (owner answer 27).

## Known differences from the JS gateway

1. **Overrun** (Go only): a body past the guard's 450M-step budget is a 400 `guardrail_blocked` where JS answers slowly
   (stream B notes 13, 26). The shadow reports it as a diff.
2. **Own spend at list price**: between snapshots the engine counts its own lines at list cost; a `billed` budget or a
   dated price version can differ until the next snapshot (at most 1 s).
3. **Own spend between snapshots** (after the final review, I1 and m1): each own line keeps its outbox seq and the spent
   its budgets had when it was emitted (its base). The estimate per budget is the largest of the snapshot's spent and,
   over the own lines in order, `base_i` plus line i and every later own line. A base was read before its line went
   out, so the sum never counts a line twice, and spend from elsewhere (JS-served calls, other keys) that reached the
   snapshot before a line is kept. A line leaves once a snapshot arrives after the control plane acknowledged its seq
   (the ack is sent after the line is stored and counted, and the gateway reads messages in order), not after a fixed
   time. (Two earlier versions were wrong: the first dropped a line as soon as a newer snapshot came, which let the
   second call of "key budget: … at the limit is 402" through on `windows-latest`; the second kept lines 10 s and took
   the oldest base, which missed spend from elsewhere between two own lines. `TestOwnSpendSurvivesTheIngestLag`,
   `TestOwnSpendKeepsSpendFromElsewhere` and `TestOwnLinesLeaveOnceASnapshotHoldsThem` pin it.) What remains: spend from
   elsewhere that lands *after* the last own line and before the next snapshot is not seen for up to 1 s, as with any
   snapshot; the estimate is a lower bound of real spend, never above it.
4. **Budget lag in the shadow**: JS decides on live spend, the engine on its snapshot; a disagreement on a *budget's*
   402 is `skipped`. A price-rule 402 the other side did not answer is a diff (review m2).
5. **Saves during a gateway start, or a slow gateway** (review m4): a save while the gateway is starting queues its
   reload and answers at once; one where the gateway does not confirm within 2 s answers anyway (a log line). Either
   window ends with the next 1 s snapshot. `/api/cost/restate` changes spend and does not reload; the next snapshot
   catches up. (P4f follow-up.)
6. **Own spend after a restart** (review m7): `Spend` is in memory; lines replayed from the outbox after a gateway
   restart are not in the first snapshot, so for about 1 s the call after a budget-exhausting one can pass (fail open by
   design). (P4f follow-up, with the ack tracking it owns.)
7. **A panic in the checks** (review m3) is the JS 500 `guardrails failed` with its line, on the serve path and in the
   shadow's compare goroutine; it is logged with the panic's text and never takes the gateway down.

## Plan deviations

- Task 2 kept guarded plans on the control plane (a temporary `untilServed` hand-off) until Task 3 wired `Serve`, so each
  commit served nothing half-built.
- Task 3's commit exposed an existing race: the snapshot lags a budget save by up to 1 s, hidden before because the
  default guardrail policy handed every call to JS. Three budget contract cases failed under go until Task 4 (Decision 25
  and own spend). Task 4 also moved the shadow's budget-lag rule forward from Task 6.
- Cost settings saves also reload the gateway (they change `keyCenter`), not only budget saves.
- `test/ipc-hardening.test.js` was updated for the snapshot-first reload; `TestHungControlPlaneBudgetsFailOpen` calls
  through 20 clients (300 simultaneous dials overflowed the listen backlog on `windows-11-arm`).
- `ZP_SHADOW_TALLY=<file>` (contract harness) appends every compare line, for the tally above.
- The adversarial heap case turns PII on (with the default policy alone the body finishes under its budget).

## The go-chat shadow diff (run 43879041468, Deno, Ubuntu)

The reviewer's explanation: in "a key revoked is refused as soon as the revoke has answered", the revoke's
`front.synced(2000)` can time out on a slow runner; the save then answers while the gateway still holds the key, JS
refuses 401 on live keys, and the go engine's compare (planned on its older state) says it would have served: a
`served` diff. P4e makes each reload a little slower (`snapshotBody()` evaluates every blocking budget before
`config.push`). The failing job's log (133339676369) holds no "did not confirm the new configuration within 2 s" line,
but that line is written to the spawned server's stderr, which the Deno contract run does not print, so its absence
does not rule the timeout out. The diff did not recur in the next three full runs, and the go-chat test now prints the
diff line if it does.
