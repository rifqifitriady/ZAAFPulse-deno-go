# P4c results: streaming chat on the go engine (slice S3)

Date: 2026-11-13. Branch `migrate/p4c-sse-plan`, which merged `migrate/deno-go` at `8889c46` (P4b, PR #8) as `eb04e56`.
Spec `docs/superpowers/specs/2026-11-13-p4c-sse-design.md`, plan `docs/superpowers/plans/2026-11-13-p4c-sse.md`
(its "Plan deviations found while building" list every change from the plan, with evidence).

## What ships

- **A sub-class `chat-stream`** of the chat route: `config.json` `gateway.engines: { "chat": "go", "chat-stream": "go" }`
  lets the go engine answer `"stream": true` chat calls to an OpenAI-format provider, on the same serving set as P4b
  (plain or no key, loopback client and Host, no guardrail check in scope, no blocking budget, no key budget, no route,
  no tool results for the token saver). A `stream_options` that JavaScript would spread into indexed keys (a non-empty
  string or array) is handed to the server. `chat-stream` has its own engine entry, shadow entry and record under the
  owner's switch rule (1 clean day, 20 compares); the default is `js`.
- **Byte-exact streams.** `gw/engine/stream.go ChatStream` ports `chatCompletion`'s line rewriter (comments and blank
  lines pass, the model name is replaced, `usage: null` and the usage-only chunk are dropped unless the client asked for
  usage, a BOM is dropped once, an incomplete UTF-8 tail at the end is dropped, invalid UTF-8 is replaced per maximal
  subpart as TextDecoder does). 17 stream fixtures written by the real JS (`scripts/fixtures/gen-chat.js`) match byte for
  byte, and every split of the input gives the same output.
- **Usage.** `stream_options.include_usage: true` is added upstream as `proxyChat` adds it (the `streamUsage` preset
  flag, `anthropic-openai` excepted); the line has the last usage chunk's tokens, the time to the first token, the cost
  of the routed model, status 200 and no error text.
- **Exactly one usage line per stream**, however it ends: the provider's end, the provider breaking off (the client gets
  a clean end without the partial line), the client leaving (the provider call is cancelled), a write error, the
  gateway's shutdown (the line is stored before the outbox closes). A gateway killed mid-stream writes none (the gap the
  owner accepted until P4f, 2026-11-13); never two.
- **Flush per provider read, synchronous writes** (a slow client slows the provider read instead of Node's unbounded
  buffering), no heartbeat of our own and no body timeout, as the JS chat stream.
- **The shadow compares streams** from the one provider stream the server read: the server keeps the provider's decoded
  text and its own client text (4 MiB cap each, and how the stream ended); the engine replays the text through
  `ChatStream` and compares the provider request, the client text and the usage line.
- **The gateway's memory:** a soft memory limit by flag, `--mem-limit-mb` (config.json `gateway.memLimitMB`, default 64,
  0 for none), not `GOMEMLIMIT`, because the gateway's environment is an allow-list (P4a E7). 4 KiB read buffer per
  stream; the line buffer is not held between events; the provider client's write buffer is 1 KiB.
- **Connection reuse:** the front proxy's and the engine's provider transports keep up to 1024 idle connections per
  host (was 64), the root cause of the first M4 runs' stalls (below).
- **Bench:** `ZP_BENCH_TIER`, the gateway's own RSS, which engine called the mock (a go run fails when the server
  answered any gateway call, or when a stream step opens more than 2 provider connections per worker), and a manual CI
  job `m4-bench`.

### The first runs and their root cause

The first local runs (`b9b09c8`, files replaced, numbers in the bench notes) stalled for about a second in front and go
modes (go 500: overhead p95 728.77 ms, gateway RSS 88.7 MB). Investigated one hypothesis at a time:
- GC (gctrace through a wrapper binary: STW ≤ 0.23 ms, live heap ~18 MB), Nagle (TCP_NODELAY on, one write per read)
  and the listen backlog itself (the same 128 cap for Node) were ruled out with evidence.
- The cause: both transports kept at most **64 idle connections per host**. Streams that end together overflowed the pool;
  the extra connections were closed and the next wave dialled again, with handshakes, TIME_WAIT growth (~100/s in a go
  step with 64, flat with 1024) and connect bursts past the macOS listen backlog, whose SYN retries take ~1 s (the stall
  size). The new bench check caught it ("603 connections for 200 streams", "1393 for 500" on CI).
- Fix `1a62f2b` (1024 per host); regression tests `TestStreamWavesReuseProviderConnections` and
  `TestForwardedWavesReuseUpstreamConnections` (86 new connections in a second wave of 150 with 64, none with 1024).
- Memory: 66.5 KiB per held stream (`TestMemoryPerHeldStream`; ~46 KiB heap, ~27 KiB stacks, mostly net/http's
  per-connection buffers; budget 80 KiB, plan Decision 19); with the 64 MiB soft limit the gateway peaks at 64–70 MB at
  500 streams.

## Differences from the JS gateway (known)

1. **Backpressure:** the engine stops reading the provider while the client is not reading; Node buffers without limit.
   The bytes are the same.
2. **A chunk JSON.parse reads and the engine's parser does not** (an escaped lone surrogate, nesting deeper than 512) is
   passed unchanged; JS rewrites its model name, and its usage would be missed (as P4b minor m1).
3. **A provider line longer than 16 MiB** ends the stream as a cut; JS has no limit.
4. **Token counts that are not whole numbers** are 0 (P4b difference 8).
5. **The JS gateway writes a left stream's line when the provider's stream ends;** the engine cancels the provider call
   and writes it at once. Both write one line with the tokens seen.
6. **The provider request keeps its body until the call ends** (an in-memory body makes net/http send headers and body
   in one write; the alternative reset connections on windows-11-arm).

## Known gaps

- A gateway crash loses the usage line of each in-flight go-served stream (owner answer 2, until P4f).
- Translated streams (Anthropic, Responses, Gemini), guardrails and budgets on streams, OAuth2 providers, routes:
  handed to the server (P4d, P4e, P4g).
- The front proxy also holds up to 1024 idle connections to the control plane; they close after 120 s idle.

## Observed flakes (not P4c)

Under parallel load only, each passes alone: `gw/guard` race tests (P4e's package), Node `test/evals-cli.test.js`,
`test/evals-claude-cli.test.js` (CLI timeout timing), `test/governance-auth.test.js` (a lockout count), Deno
`test/secret-binding.test.js` ("openrouter made a request").
