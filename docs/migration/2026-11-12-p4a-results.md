# P4a results: the Go gateway in front (slice S1)

Date: 2026-11-12. Branch `migrate/p4-go-data-plane`. Spec `docs/superpowers/specs/2026-11-12-p4a-go-front-design.md`,
plan `docs/superpowers/plans/2026-11-12-p4a-go-front.md`.

## What ships

- `gateway.engine` in `config.json`: `"js"` (the default) is the server alone on the main port, as before P4a; `"front"`
  puts `zaafpulse-gw` on the main port (TLS when `ZAAFPULSE_TLS_CERT`/`ZAAFPULSE_TLS_KEY` are set) in front of the
  server's internal listener on `127.0.0.1`. Every route class is on `js`: the gateway forwards everything.
- The client of each forwarded request travels in `X-ZP-Client: <ip> <port> <tls> <hmac>` (HMAC-SHA256 with the
  per-start `frontToken`); the server checks it and its six peer readers use it. Without sign-in a client from another
  machine is refused.
- The supervisor restarts the gateway with back-off (1 s to 30 s). Exits 1, 2, 4 and 5 with a `fatal: ` line, a
  binary that cannot be started at all (missing, not a program, not granted to `deno run`), or a sixth exit within
  60 s, are the `failed` state: the server then listens on the main port itself (`fallback`), logs
  `gateway failed: <reason>; serving on Deno`, and the Overview chip turns red. `GET /api/gateway/status` (owner only)
  returns the state, the mode and the engines.
- The host check answers in front mode what it answers in js mode: a request without a Host reaches the server with
  none (Go flags it with `X-ZP-No-Host`, the internal listener removes the Host Go had to write), and an absolute-form
  target is refused with 400 in both modes (deviation 15).
- The mark file (`.data/ipc-marks.json`) is written after the stores, with a rename, and neither is fsynced. The order
  holds while the OS runs; after a power loss the disk may hold the new mark without the store's last lines, so the
  mark can lead the store and a replay skips those events. P4a has no real Go events; P4f must fsync the store before
  the mark or accept and document the loss (P4f entry condition 4).
- The P3 entry conditions E1 to E11 are met (table below). IPC v1 gained two optional fields: `config.push.front`,
  `secrets.handoff.frontToken`.

## Differences from the spec

1. **The client travels in a signed header, not a connection preamble (D3).** The probe failed on Deno 2.9.8 (an
   `http.Server` handed a socket with `emit('connection')` answers only the first request on it), and Go's pool shares
   upstream connections between clients. Task 3 built the spec's fallback: `X-ZP-Client: <ip> <port> <tls> <hmac>` on
   every request, checked by the internal listener. Spec D3 and the T4 row were updated in Task 4.
2. **Forwarding headers pass through; they are not removed (D2).** The server reads their presence as "a proxy is in
   front". Go forwards `X-Forwarded-*`, `Forwarded`, `Via`, `X-Real-IP`, `CF-Connecting-IP` and `True-Client-IP`
   exactly as the client sent them, also when the client names them in `Connection` (Node keeps them; restored in
   the final fix round, review m1), and adds none. Other headers a client names in `Connection` are dropped, as
   hop-by-hop headers. `ZAAFPULSE_TRUST_PROXY` keeps its meaning without being passed to Go.
3. **Six peer readers, not four (D3), and the `Origin` rule is not one of them.** All six use `peerAddress()` /
   `peerEncrypted()`. Because the `Origin` rule reads only the header, the auth mode is what keeps front mode safe;
   Task 5 adds a second guard (H1): without sign-in, a client Go names from another machine is refused
   (`peerMayConnect`), even when it writes `Host: 127.0.0.1`. `pickMode` and `SERVER_MODE` keep reading `HOST`, the
   public listen host Go holds, never the internal `127.0.0.1`.
4. **One contract case is relaxed in front mode, by the coordinator's call.** Go's `net/http` refuses a malformed
   request target before any handler, so its plain-text 400 cannot be changed without replacing the server. The case
   `GET /v1/models/{id} with broken URL encoding: 400` keeps asserting status 400 and, only under `ZP_ENGINE=front`,
   accepts Go's body `400 Bad Request` as well as the JSON message. No real client sends such a request.
5. **`runScope` does not reach the single-file binary (D7).** P4a grants the gateway binary to `deno run` launches (the
   service install, the tests, the preview). `front` mode in a compiled binary needs the gateway shipped beside it and a
   baked grant: P6. The compiled binary keeps working in the default `js` mode.
6. **`/api/gateway/status` collides with the admin-route pattern.** The route is matched before it. It is owner-only: it
   is not added to `lib/users/policy.js VIEWER_READS`, so the existing role check refuses everyone else, and the
   Overview chip stays hidden for them.
7. **E3: no raw usage writer exists.** The ingest builds its own `createUsage` on the same `gateway-usage.jsonl`, as
   `lib/ipc/local.js` does, and uses the server's raw governance, MCP audit and trace stores. A second
   `createGovernanceAudit` on the same folder would fork the HMAC chain, so it is not used in the server.
8. **E8 needs more than the exit code.** On Windows a hard kill (`taskkill /F`, `TerminateProcess`) exits 1 with no
   signal, the same code as a damaged outbox, and must be restarted. The supervisor enters `failed` on 1, 2, 4 or 5 only
   with the gateway's `fatal: ` stderr line (or when this side refused the hello). Task 2 adds the line (`exitWith`).
9. **E5: the schemas are listed one by one**, and "a test on the compiled binary" is the `doctor` line
   `Gateway IPC  v1, 15 schemas`, checked by `scripts/smoke-binary.js` in the six-target CI job.
10. **The 2 s first-request close of the internal listener is lengthened in front mode.** Go's `http.Transport` can pool
    a connection it dialed but never used, and the listener closed such a connection after 2 s, which fails a
    non-replayable POST with 502. `createFront` passes `firstRequestMs: 130000` (longer than Go's 120 s idle timeout),
    so Go always closes a spare pooled connection first; the default stays 2 s. Consequence: the internal port holds a
    local connection that never sends a request for up to 130 s (open minor T5-M5).
11. **Spec line references** are a few lines off at 464daf6: `gateway.handle` is at `server.js:1497` (spec 1511), the
    trace check at `server.js:1483-1486` (spec 1493), the loopback `Origin` rule at `lib/auth.js:165` (spec 160).

Found in the Task 5 review and not in the plan:

12. **N1: no front retry after a crash-loop fallback.** D5 says a later `reload` or `zaafpulse restart` tries `front`
    again. After a fallback caused by the restart limit (`kind: 'restarts'`), `reload()` returns false: no retry on any
    save, only a restart of ZAAFPulse tries `front` again. After a fatal-exit fallback (kind `'fatal'`), a change to
    the `gateway` section still retries; that was the default of owner question 1 (the coordinator's decision, pending
    the owner's answer). The chip should say a restart is needed in the crash-loop case (open).
13. **The 2 s graceful close on retry.** The bounce in `lib/front` closes the server's main listener gracefully:
    `server.close()`, then `closeIdleConnections()`, then `closeAllConnections()` only after 2 s, so long streams
    (SSE) get up to 2 s before their connections are cut.
14. **`onFailed(reason, { kind })`.** The supervisor's `onFailed` callback gained a second argument `{ kind }`:
    `'fatal'` for the four fatal exits, `'restarts'` for the restart limit. An additive change; `lib/front` uses it for
    deviation 12 (`test/ipc-hardening.test.js`).

Found in the final review and fixed in its fix round:

15. **The Host a request came with, in front mode (review I1).** Go's `net/http` accepts an HTTP/1.0 request without
    a Host, and its transport then writes the upstream address, so the server saw `Host: 127.0.0.1:<internal port>`:
    a request js mode refuses (403) was answered, `ZAAFPULSE_ALLOWED_HOSTS` was skipped, and `publicBase` advertised
    the internal port. Go cannot send an empty Host, so it sets `X-ZP-No-Host: 1` (replacing any copy the client
    sent) and the internal listener removes the Host and the flag. For an absolute-form target, `net/http` keeps the
    target's host and drops the Host header (RFC 9112 3.2.2), while the server's host check reads the header, as Node
    gives it. Go cannot hand that header on, so the target is refused with 400 `absolute-form request targets are not
    accepted`, **and `server.js` now refuses it the same way in js mode** (before, js mode checked the Host header and
    answered). Browsers and API clients never send that form to a server; only clients talking to a forward proxy do.
    Tests: `test/front-host.test.js` (js and front side by side, on Node and Deno), `gw/front/front_test.go`,
    `test/front-internal.test.js`.
16. **A gateway binary that cannot be started fails at once (review T5-M3).** A spawn error with no process
    (`ENOENT`, `EACCES`, Deno's `NotCapable`) is the `failed` state (kind `'fatal'`, so a later gateway save may retry
    front once the binary is built), not a crash to restart: the fallback holds the port within moments instead of
    about 31 s. Tests: `test/ipc-hardening.test.js`, `test/front-server.test.js`.

## P4b (and P4f) entry conditions

Numbered as in the final review. Condition 7 and the review's I1 and m1 (which it would have made conditions 0a and
0b) were fixed in the final fix round, so they are no longer entry conditions.

1. **A separate usage writer and in-memory spend.** The ingest's own usage writer (deviation 7) shares
   `gateway-usage.jsonl` with the gateway's: the server's in-memory caches, and so per-key budgets, do not see the Go
   engine's lines. P4b must route Go's usage through the one writer that feeds the spend (P4f at the latest) before any
   per-key budget is enforced on a `go` route (T2-b).
2. **Route classification on the same path form.** Go must classify routes on the same path form as `gateway.handle`
   (the encoded request path); today Go classifies the decoded path. With every route on `js` this is harmless; with
   the first `go` route it is not (T4-d).
3. **A late `front` section is ignored.** A `front` section that appears in `config.json` after the gateway started
   (without a restart or a retry) is not applied; P4b's converter and reload path must define when it takes effect
   (T4-e).
4. **P4f, before Go emits real usage, audit or trace events:** outbox `Close` under `sendMu` and idempotent (T1-a,
   T1-b); fsync the store before the mark file, or accept and document the power-loss order (T2-a, "What ships"); and
   re-seed the marks per session (re-read the mark file and the tails when a new session starts), so that a second
   server on the same data folder cannot replay over stale in-memory marks.
5. **Proxy and CA variables reach the gateway** on an allow-list (`HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY`,
   `SSL_CERT_FILE`, `SSL_CERT_DIR`) before the first `go` route calls a provider (T2-e).
6. **Header and limit parity with Node on the public port:** `MaxHeaderBytes` at Node's limit, so an oversized header
   gets 431 rather than 502 (m2), and Go's log noise filtered or rate-limited (m3).
7. *(Met in the final fix round: a missing or unrunnable gateway binary is `failed` at once, deviation 16.)*
8. **The owner answers question 1** (fallback retry on a gateway save: T5-N2, deviation 12), and the chip says "restart
   needed" after a crash loop (T5-N1).

- The `t.after` lesson: `node:test` runs a test's `t.after` hooks in the order they were added (first in, first out),
