## What ships, per slice

- **P6a, build and package.**
  - `deno task build --package [--target …]` builds `zaafpulse` (`deno compile`, the `cli` set) and `zaafpulse-gw`
    (`CGO_ENABLED=0 go build -trimpath -buildvcs=false -ldflags "-s -w -X main.version=<v>"`) for one target. It packs
    both with `LICENSE` into `zaafpulse-<v>-<name>.tar.gz`, or a `.zip` for the `win-*` targets, and lists the archives
    in `SHA256SUMS.txt`.
  - The zip is written in JS, reproducible (fixed time, unix modes `0755` on the `.exe` files), so a Windows package
    builds on any host. A Windows host refuses `.tar.gz` targets (MSYS tar drops the execute bit).
  - On macOS the darwin gateway is ad-hoc signed with `codesign --sign -`. The Go linker signs only darwin/arm64, which
    the dry run caught.
  - `zaafpulse-gw -version` prints the version, which is also `hello.gwVersion`.
  - The compiled binary may start its gateway:
    - the `cli` set names `zaafpulse-gw` in `run`, granted through `PATH`;
    - the installers' command and the service file put the install folder first;
    - a missing or refused gateway fails the first start at once and falls back, with the reason in the status, on the
      Overview chip and in `doctor`'s new gateway line.
  - `scripts/smoke-binary.js <bin> --front <gw>` proves the unpacked package with the gateway in front.
- **P6b, health on the Overview.**
  - `GET /api/gateway/status` gains `gwVersion`, `version`, `versionMismatch`, `binary { path, found, allowed }` and
    `healthAgeMs`.
  - The topology card's chip shows `ready · v<version>`, turns amber on `· stale` (no health for over 5 s) and on
    `· version differs`, and its tooltip carries uptime, in-flight calls, outbox depth, snapshot age, restarts and the
    last failure.
  - The supervision policy is unchanged from P4a: back-off of 1 s doubling to 30 s, a fallback after 5 restarts in
    60 s.
- **P6c, installers.** `install.sh` and `install.ps1` install both binaries from this repo's release, checked against
  `SHA256SUMS.txt`, with an optional `gh attestation verify` (`--verify-attestation`). In detail:
  - **New flags:** `--archive` / `--sums` install a local package.
  - **Upgrade:** a run over v1.x or v2 keeps one generation in `<prefix>/rollback/` (`VERSION` says which), after
    checking that the new binary runs.
  - **Rollback:** `--rollback` swaps back.
  - **Uninstall:** removes only the installer's folders; the data stays.
  - **Removed:** v2 downloads no Node, and `--source` and `--version main` are gone. The v1.x-only platforms (musl,
    armv7l, ppc64le, s390x, 32-bit Windows) get a pointer to the v1.x installer.
  - **Windows server stop (fixed in `lib/service.js`):** the Windows service stop now finds a server started by the
    quoted Startup launcher. The installer ends what still runs from the install folder after a stop.
- **P6d, M12.** `scripts/upgrade-check.js` runs v1.1.0, then v2 with the gateway in front, then v1.1.0 again on one data
  folder, through each version's API.
- **P6e, workflows.**
  - `build.yml` (new, reusable) runs the six native builds: package, `codesign --verify` on macOS, the smoke test with
    the gateway in front, the M6 size against v1.1.0, and the artifacts. `ci.yml`'s `build-deno` calls it.
  - `release.yml`:
    - **On a `v*` tag push:** tag = version, the suites, build, install-test, then `publish`. `publish` is the only job
      with write permissions; it attests, then runs `gh release create --verify-tag`.
    - **On a manual run:** always a dry run (build, install-test, `assemble` → artifact `release-dry-run`). It never
      attests, publishes or tags.
  - `scripts/install-test.sh` and `install-test.ps1` run on the six runners: a clean install, an upgrade from the v1.1.0
    installer at its tag followed by `--rollback`, and M12 on linux-x64 and win-x64.
- **P6f, docs.** `docs/install.md` covers the packages, both installers, upgrading from v1.x, both ways to roll back,
  and "Unsigned binaries: first start and verifying a download" (Gatekeeper, SmartScreen, `SHA256SUMS.txt`,
  `gh attestation verify`). The README install rows point at this repo's release. `docs/release-hardening.md` gives
  the tag ruleset and immutable-release commands for this repo.

## Known differences from v1.x

- **Install:** v2 is installed from this repo's release assets (`releases/latest/download/install.sh`), not from
  `raw.githubusercontent.com/rifqifitriady/ZAAFPulse/main`. Upstream's `install.sh` and `install.ps1` will conflict at
  the weekly upstream merge; keep this repo's.
- **Platforms:** no v2 build exists for musl/Alpine, armv7l, ppc64le, s390x or 32-bit Windows (the v1.x installer
  still serves them). The Docker image stays on Node until P7.
- **Release assets:** archives only; there are no loose binaries. A binary started from an unpacked archive outside
  `PATH` serves on its own and cannot put the gateway in front. The fallback reason says so.
- **Uninstall:** `--uninstall` keeps the data. v1 deleted the Linux user data folder inside the prefix.
- **Rollback with the v1.1.x installer:** run `zaafpulse service uninstall` (v2) first. On Windows, also delete the
  two `.exe` files from `%LOCALAPPDATA%\ZAAFPulse\bin`.
- **Version:** `package.json` is still `1.1.0`, so packages are named `1.1.0`. The bump to 2.0.0 is P7's.

## Manual steps for the owner (in order)

1. **Repo settings, before the first tag** (`docs/release-hardening.md`, section for ZAAFPulse-deno-go): apply the
   tag ruleset "Release tags are permanent" and immutable releases. Check that `gh api
   repos/rifqifitriady/ZAAFPulse-deno-go/rulesets` lists the ruleset and that `gh api
   repos/rifqifitriady/ZAAFPulse-deno-go/immutable-releases` says `"enabled":true`.
2. **Optional, before the tag:** the second dry run (Q4).
3. **Version (P7):** set `package.json` `version` to `2.0.0`, commit on `migrate/deno-go` (or the branch that releases),
   and merge.
4. **Tag:** `git tag v2.0.0 <commit> && git push origin v2.0.0`. `release.yml` checks the tag against `package.json`,
   runs the suites, builds, runs the install tests, and publishes. Watch it with
   `gh run watch -R rifqifitriady/ZAAFPulse-deno-go $(gh run list -R rifqifitriady/ZAAFPulse-deno-go --workflow release.yml -L 1 --json databaseId -q '.[0].databaseId')`.
5. **Verify the release:**
   ```sh
   gh release verify v2.0.0 -R rifqifitriady/ZAAFPulse-deno-go
   mkdir rel && cd rel && gh release download v2.0.0 -R rifqifitriady/ZAAFPulse-deno-go
   shasum -a 256 -c SHA256SUMS.txt
   for f in *.tar.gz *.zip install.sh install.ps1 SHA256SUMS.txt; do gh attestation verify "$f" --repo rifqifitriady/ZAAFPulse-deno-go; done
   ```
6. **The exit's public-release leg, on each of the six platforms.** Use a test user or VM, not the owner's live install:
   the launchd label is shared.
   - **macOS (arm64, x64) and Linux (x64, arm64).**
     - Clean install: `curl -fsSL https://github.com/rifqifitriady/ZAAFPulse-deno-go/releases/latest/download/install.sh | sh`,
       then `zaafpulse doctor` (the gateway is found and allowed) and open http://localhost:4777.
     - Upgrade from v1.1.0 on a machine with nothing installed:
       1. Install v1.1.0:
          `curl -fsSL https://raw.githubusercontent.com/rifqifitriady/ZAAFPulse/v1.1.0/install.sh | sh -s -- --version v1.1.0`.
       2. Use the dashboard once.
       3. Run the v2 command above.
       4. Check that the data is there, and that `cat ~/.local/share/zaafpulse/rollback/VERSION` shows `v1.1.0`.
       5. Roll back: `curl -fsSL https://github.com/rifqifitriady/ZAAFPulse-deno-go/releases/latest/download/install.sh | sh -s -- --rollback`.
       6. Check that v1.1.0 serves the same data.
   - **Windows (x64, arm64), in PowerShell.**
     - Clean install: `irm https://github.com/rifqifitriady/ZAAFPulse-deno-go/releases/latest/download/install.ps1 | iex`.
       SmartScreen asks once per `.exe` only for a browser download.
     - Upgrade from v1.1.0:

          `& ([scriptblock]::Create((irm https://raw.githubusercontent.com/rifqifitriady/ZAAFPulse/v1.1.0/install.ps1))) -Version v1.1.0`.
