## What ships, per slice

Every slice merges on its own and reverses by config. With no `egress` section in `config.json` the product behaves
as at `6a9800a`: every class is `direct`, the allow-list only reports, and the lock-down is off.

- **P5a, the proxy and its records.**
  - The Go side is `gw/egress`, served on `127.0.0.1:0` by `zaafpulse-gw` in front mode and opened before `ready`, which
    carries the port. It has three paths: a forward endpoint (`X-ZP-Egress-URL`, `-Purpose`, `-Redirect`, `-Public`), a
    verdict-only `/check`, and a `CONNECT` tunnel.
  - The token is `HMAC-SHA256(frontToken, "zaafpulse egress v1")`, compared in constant time. A missing or wrong token
    gets no reply.
  - Redirects follow fetch's rules in Go, with each hop checked and recorded. Go asks for gzip and decodes it. Failures
    come back as `TypeError("fetch failed", { cause: { code } })`.
  - Public mode refuses private addresses at connect time. The address set is shared by `lib/net.js` and Go, and is
    proven by `gw/testdata/egress/private.json`, written by the JS.
  - Every call is recorded as a new IPC type, `egress.event`, durable in the outbox and stored in `.data/egress.jsonl`.
    That includes each redirect hop and every provider call or token fetch the Go engine makes itself (`via: engine`).
    A refused call also gets an `egress.refused` entry in the audit chain.
  - The client is `lib/egress.js`: unconfigured it is plain `fetch` and `net.connect`. Loopback targets always go
    direct.
- **P5b, every caller class through its switch.** Each class is set with `egress.classes.<class>`: `direct`, `check`
  (the call goes direct and `/check` records the verdict, `via: check`), or `go`.
  - A class asked for `go` moves only after its gate passes: the owner's rule of 1 clean day and 20 checks.
  - The gate is sticky (`.data/egress-gate.json`): a class stays on `go` until a check disagrees or the owner moves the
    class back.
  - Every call site from the inventory now goes through the client (table below).
  - The stdio MCP server finds the dashboard's endpoint through `.data/egress.json` (mode 0600, removed on stop).
- **P5c, the allow-list.** `lib/egress-allow.js` builds it from `config.json`, `agents.json` and the environment, with
  exact ports; Roam's peer wildcard takes any port. It is pushed with every config change and checked by the minute
  loop. `egress.allowList` is `report` (the default) or `enforce`.
- **P5d, the Compliance control.** The control is `network_egress`, "Network egress is mediated and logged" (MEASURE
  2.7, A.6, Art. 12). `GET /api/egress` is owner only, cached for 10 s, with bounded reads.
- **P5e, the lock-down.** `egress.lockdown: true` adds `--allow-net=127.0.0.1,localhost,[::1]` (plus the listen address
  when it is not loopback) to the server's `deno run` launch line. It applies only when all of these hold:
  - the gateway runs in front mode;
  - every class is asked `go` and has passed its gate;
  - the listen host is an address.

  While no gateway is ready, a locked client fails with `EGRESS_UNAVAILABLE` and never goes direct. The fallback is
  `"lockdown": false` and a restart (for a service, `zaafpulse service install` again), or
  `ZAAFPULSE_EGRESS_LOCKDOWN=0`, which wins over the config. The status says when a narrowed grant outlives the
  fallback.

the caller got the same answers, apart from the known differences below. Each call left its record.

**Denial proof (M10)** (`test/egress-lockdown.test.js`, Node and Deno). A probe is launched with exactly the
locked-down line that `selfCommand` computes.
- Refused before any packet:
  - `fetch` to `example.com`, `10.0.0.1`, `169.254.169.254`, `[2001:db8::1]` and `127.0.0.2` throws Deno's
    `NotCapable`;
  - `net.connect` to those addresses throws `NotCapable`;
  - `net.connect` to a name fails at the lookup with `getaddrinfo EPERM`, so no query leaves.
- Still working: `127.0.0.1` answers directly, and the same kind of call reaches the fake through the real gateway's
  endpoint, where it is recorded.
- With no endpoint, the locked client fails with `EGRESS_UNAVAILABLE`.
- A separate case proves a CLI `--allow-net` that names `169.254.169.254` is still refused by the set's deny.

## Known differences from a direct call

These are the spec's, plus those found in the plan deviations.
1. Requests advertise `accept-encoding: gzip` only. A gzip answer arrives decoded, without `content-encoding` or
   `content-length`.
2. A failure is `TypeError("fetch failed")` with `cause.code` on both runtimes.
3. Go applies the proxy environment for every class except public mode, which never uses a proxy.
4. Trusted roots are Go's: the system's, plus `SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS` and `DENO_CERT`.
5. Recorded byte counts are of the decoded body.
6. A gateway restart cuts the egress calls in flight.
7. The private-address set is stricter on both runtimes (spec known difference 7).
8. Local runtime probes now follow https URLs too.
9. `Response.type` is `default`.
10. An AI client registered before P5 cannot check the dashboard's pid, so its tool calls go direct until it is
    registered again.

## Owner questions (recommendation taken; nothing blocked)

- **Q1 (P6):** should the single-file binary have the narrow net grant baked in? Recommended: not in P5. The binary
  locks in the client only, and the control says so.
- **Q2 (P6):** should the stdio MCP server's own grant be narrowed? Recommended: not in P5. It uses the dashboard's
  endpoint when one runs.
- **Q3 (P7):** should `enforce` and `lockdown: true` become the defaults at the cut-over? Recommended: yes, after the
  owner has run with them on the preview.

## Benchmarks

No overhead figure was measured for P5. The loopback hop adds one local HTTP round trip to a call of a class on `go`;
it is **not quiet-confirmed**. It joins the deferred list for the program's final quiet-machine step, as M3 for a
call through the egress endpoint: the overhead of a `connectors` call on `go` against `direct`, with a local fake.
