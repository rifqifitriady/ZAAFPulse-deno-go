## Group F

Two tests, one cause. Both wait on a promise whose only timer is deliberately unref'd, against a fake that holds no
socket or handle:

- `test/evals-models.test.js` "external: the timeout aborts the request, not only the wait": the call timer in
  `lib/evals/models.js` is unref'd and always cleared in `finally`; the fake `complete()` waits for the abort signal.
- `test/evals-api.test.js` "evals api: a slow Claude Code search answers checking…": the wait timer in
  `lib/evals/api.js settingsGet` is unref'd; the fake `claude.available()` is `new Promise(() => {})`.

Under Deno both fail with "Promise resolution is still pending but the event loop has already resolved"; under Node
both pass. Probes: a `node:test` file whose only work is an unref'd `setTimeout` fails under Deno and passes under Node,
and the same file with a ref'd timer passes on both. A hanging `http` server sees the socket close 56 ms (Deno) and
53 ms (Node) after `AbortController.abort()`, so the product's abort reaches the socket on both runtimes. A real call
holds a socket that keeps the loop alive, so the product behaves the same on both runtimes. Fix: each test keeps a
ref'd `setInterval` for its duration and clears it in `finally`. No product change.

## The permission matrix (T5)

`deno.json` holds four sets: `test` (Task 4), `server` (server.js, `zaafpulse start`), `cli` (bin/zaafpulse.js) and
`mcp-stdio` (mcp.js). The reason for every entry is in `lib/permissions.js` `WHY`; `test/permissions.test.js` fails
when the two drift and proves each permission by denial (a probe run under `deno run --no-prompt -P=<set>` with the
launch's write scope).

| Permission | server, cli, mcp-stdio | Why |
|---|---|---|
| read | all | agent logs under the home folder and owner-chosen folders; runtime detection in `/opt/homebrew`, `/usr/local`, `/Applications` |
| write | all in the file; each `deno run` launch passes `--allow-write=<writeScope()>`, which replaces it | the data folder and temp; server and cli add the skill folders and the AI clients' config folders (never the home folder); cli adds the service folders. The compiled binary keeps unscoped write (its paths are fixed at build time) |
| net | all but `169.254.169.254` and `metadata.google.internal` | providers, connectors and price sync until P5 moves egress to Go |
| env | all | owner decision O1: a v1 secret reference may name any variable |
| sys | allow-list: homedir, uid, gid, userInfo, systemMemoryInfo, osUptime, loadavg, cpus, umask; plus hostname (server, cli) and osRelease (cli) | `os.userInfo()` needs uid, gid and userInfo together |
| run | allow-list (owner decision O2: anything else is refused loudly) | ps, lsof, vm_stat, the keychain tools, notifications, launchers, claude, codex, node, the model server presets, the owner model servers approved in Settings; cli adds the service tools |

**Run is not a sandbox boundary.** The run list includes interpreters and launchers (node, osascript, powershell,
powershell.exe, cmd, open, xdg-open, brew, claude, codex, launchctl; for cli also wscript.exe, explorer.exe, schtasks,
systemctl).
Each runs any code it is given, outside Deno's permissions, so run (and therefore write) is not a sandbox boundary:
the write scope guards against accidents, not a determined attacker. They stay because features need them (reasons
in `lib/permissions.js` `WHY.run` and `WHY.launchers`). The **Runtime permissions** control names the ones the running
process holds and stays `partial` while it holds any.

**Launch lines are checked** (security review of T5). Every `--allow-write` and `--allow-run` entry of a `deno run`
launch is refused, naming the value, when it holds `,` `"` or a control
character: a comma would split one entry into two grants (`ZAAFPULSE_DATA=…/x,/` would grant write to `/`), and a quote
or line break would break the Windows launcher (VBScript running cmd.exe). Names such as `O'Brien` or `AT&T` pass; each
generated file escapes for its own syntax. Only owner model servers approved as
their command is now are added to `--allow-run`. The Windows launcher refuses an argument with `"` or `%`, and the
systemd unit escapes `%` and `$`. `permissions.kill()` takes only an integer pid other than 0 and -1 and the signals
0, SIGSTOP, SIGCONT, SIGINT, SIGTERM, SIGKILL; it runs the `kill` program in the C locale, and a kill that fails for
another reason than ESRCH or EPERM is reported with its own text, never as "the process is gone".

Denial evidence (macOS arm64, Deno 2.9.8): writes outside the scope (`~/.ssh`, the home folder, `~/Library/LaunchAgents`
from `server`, the skill folders from `mcp-stdio`) fail with `Requires write access to …`; the metadata hosts fail with
`Requires net access to "169.254.169.254"`; `curl` fails with `Requires run access to "curl"`; `os.networkInterfaces()`
and, for `server`, `os.release()` fail with `Requires sys access`. A walk of 27 pages and APIs of the real server
launched exactly as `lib/service.js startCommand()` builds it answered 200 everywhere, installed the skills into both
folders, registered Kiro's MCP entry (as a `deno run -P=mcp-stdio` command) and logged no refusal.

### Signals need the `kill` program under a run allow-list

Deno's `process.kill` needs an unscoped run grant: under any `--allow-run=<list>` it refuses every signal, even 0, with
`NotCapable: Requires run access` (measured on macOS, Deno 2.9.8). Agent control, the model server controls and the
judge's process-group stop would all have failed (agent control would even have reported a live process as gone).
Owner decision O2 keeps the run allow-list, so `lib/permissions.js kill()` sends the signal through the `kill`
program (added to the `server` and `cli` lists) whenever the run grant is scoped, and turns its "No such process" and
"Operation not permitted" into the `ESRCH` and `EPERM` errors `process.kill` throws. Under Node, or with an unscoped
run grant, `process.kill` is used as before. Checked end to end under `-P=server`: pause (state `T`), resume and stop
of a stand-in Claude Code on macOS and on Linux (Docker, Debian, procps and lsof installed).

### Linux: no scoped route to `/proc`

Deno 2.9.8 on Linux refuses every read under `/proc` unless the process holds all permissions; `--allow-read=/proc`
and `--allow-sys` do not help (Task 4). The sets never grant all, so on Linux:

- processes come from `ps`, and for each AI agent process argv comes from `ps -o comm` and the working folder from
  `lsof`, the way macOS already works, so agent control and linking a session to its process keep working;
- used memory comes from `os.totalmem() - os.freemem()` (the same MemAvailable figure);
- Docker is detected by `/.dockerenv` only, and a model server's systemd system unit is not seen (it shows as a plain
  process); each is said once on stderr;
- without `ps` (a minimal image without procps) nothing can be listed; this is said once and shown the same way;
- without `lsof` the working folders are unknown, so agent control and session linking are unavailable: the server log
  says so once, and the Compliance controls **Runtime permissions** and **Pause and stop an agent** turn `partial` with
  that text.

## The compiled binaries (T6)

`deno task build` (`scripts/build-deno.js`) compiles the committed tree with `deno compile -q --no-prompt -P=cli
--no-check`, one `--include` per shipped path, and writes `dist/zaafpulse-<version>-<name>[.exe]` and
`dist/SHA256SUMS.txt`. Nothing is unpacked at start (spec D2). The CI job `build-deno` builds each target on a runner of
its own OS and CPU and runs `scripts/smoke-binary.js` on it: `version`, `start --demo` on a throwaway data folder until
`/login.html` answers 200, `/api/platform` says `single: true, runtime: "deno"`, and `doctor` exits 0.

Result, CI run 42932795829 on the branch head `fb99293` (all 13 jobs green, the six `build-deno` jobs each `ok: true`;
`startupMs` is demo start to first 200 on that runner, so it measures the runner as much as the binary):

Deviations from the plan, found by running it:

- **The binary holds the `cli` set, not `server`.** The binary's entry is `bin/zaafpulse.js`, which also runs `doctor`,
  `service install` and `mcp`. Under `-P=server` `doctor` fails with `Requires sys access to "osRelease"` and the
  service tools are not on the run list. `cli` is a superset of `server` and `mcp-stdio`. The cost, recorded as debt
  for M9/P5: `zaafpulse start` and `zaafpulse mcp` in the binary hold the wider `cli` run list (the service tools
  `systemctl`, `loginctl`, `useradd`, `chown`, `schtasks`, `wscript.exe`, `explorer.exe` on top of `server`; on top of
  `mcp-stdio`, every launcher of `server`) and an unscoped write, since a set's paths are fixed at build time. A `deno
  run` launch of the same entry points holds its own narrower set and the computed write scope.
- `deno task build` starts `deno compile` by the name `deno`: under `deno task` the script's `process.execPath` is the
  symlink-resolved Cellar path, which `--allow-run=deno` does not match, and the spawn then fails with no message.
- The tar extraction runs with relative names: GNU tar from Git Bash on Windows reads `D:\...` as a host name.
- The smoke test sets `ZAAFPULSE_AUTH=none`: demo mode asks for a sign-in on a Linux machine with other login users,
  which a CI runner has.
- `lib/service.js`: a launchd or systemd service of a single-file binary gets the data folder as its working folder (the
  app folder exists only inside the binary).

## Open items for the gate

- **O1** env: all (decided 2026-11-10; every set holds `"env": true`).
- **O2** the run allow-list (decided 2026-11-10: keep the list): refusals are loud; owner runtimes outside the presets and an IDE-only Claude Code are
  refused in a compiled binary.
- **O3** the startup miss above: accepted (2026-11-11).
- **Gate CI run:** 42960351818 on `aa1adcb`, all 13 jobs green (Node on 4 OS, Deno on ubuntu and macOS, typecheck, the
  six `build-deno` targets). The 48 h live run was dropped by the owner (2026-11-11).
- A full-knob bench of the binary on power (2,000 requests, 50/200/500 streams) is still to be recorded.
- **Service PATH and the run grant** (final review, fixed). launchd gives a user agent
  `PATH=/usr/bin:/bin:/usr/sbin:/sbin`, and Deno grants an `--allow-run=<name>` only when it finds the name on PATH at
  start; a name it cannot find is not granted, and neither is that program by its absolute path (measured: `env -i
  PATH=/usr/bin:/bin deno run --allow-run=brew` spawning `/opt/homebrew/bin/brew` is refused; with `/opt/homebrew/bin`
  on PATH, or with `--allow-run=/opt/homebrew/bin/brew`, it runs). Deno matches the literal path: granting the target of
  a symlink does not grant the link. The product starts Claude Code, its node, brew and the model servers by the
  absolute path it looked up. Fix: `service install` writes the install-time PATH (absolute entries without `,` `"` or
  control characters, de-duplicated, then the usual system folders) into the plist, the systemd unit and the Windows
  launcher (`lib/service.js serviceEnv`), and `runScope()` adds every absolute path the product's own lookups resolve
  for `claude`, `node`, `brew`, the preset model servers and approved owner runtimes (`lib/permissions.js lookedUp`).
  `test/service-path.test.js` reproduces the minimal PATH with a Deno child.
- **The compiled binary and the service PATH** (measured, Deno 2.9.8, macOS arm64): a binary built with `-P=<set>`
  keeps the run list as names and resolves them against the PATH of the process **when the binary starts**, not of the
  build machine (a binary compiled under `PATH=/usr/bin:/bin` runs `/opt/homebrew/bin/brew` when started with
  `/opt/homebrew/bin` on PATH; the same binary started under `PATH=/usr/bin:/bin` is refused). The service PATH above
  is therefore what makes the binary's baked `cli` list work as a service; `runScope()` does not apply to it. A program
  outside every PATH folder (Claude Code in `~/.claude/local` only, an IDE-only Claude Code) stays refused in the binary
  (O2, loud).
- **Grants are frozen at install.** The write and run scopes, the approved owner runtimes and the PATH are written into
  the service file and the MCP client entries when they are made: after approving a runtime, moving Claude Code or
  changing `CLAUDE_CONFIG_DIR`, run `zaafpulse service install` (and the MCP registration) again (`docs/install.md`).
- **Windows under scoped Deno: signals** (final review, fixed). `process.kill` is refused under a run allow-list on
  Windows too. Liveness (signal 0) now asks `tasklist /FI "PID eq <pid>" /NH /FO CSV` (added to the `server` and `cli`
  run lists), so a model server stop by `taskkill` is reported as done and agent control lists candidates without an
  error. Real signals are not sent on Windows: stop goes through `taskkill` as before, pause and resume stay
  unavailable there, and `permissions.kill()` refuses a real signal on Windows under a scoped grant with a message
  that names `taskkill`. Under Node, or with an unscoped run grant, Windows keeps `process.kill`. Tested through the
  injected `deno`/`platform`/`spawn` seams on every OS; not yet run end to end on a Windows machine under `deno run`.
