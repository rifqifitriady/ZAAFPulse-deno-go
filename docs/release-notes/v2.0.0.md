ZAAFPulse v2.0.0 is the first release from this repository. It is the same dashboard, API, port (4777), sign-in and
data folder as v1.1.x, rebuilt as two programs: a Deno control plane and a Go gateway. Out of the box it behaves as
v1.1 does; the Go parts are switched on by you, one class of traffic at a time.

v2.0.0 ships packages for **Linux and Windows only**. There is no macOS package in this release: on a Mac, keep using
v1.x (see [Platforms](#platforms)).

The final quiet-machine benchmarks (M3, M4 and the stream baseline) have **not** been run yet. They are published
after this release; see [Verification status](#verification-status).

## What v2 is

- **Two programs.** `zaafpulse` is the dashboard and everything it did in v1.x, now a single-file Deno binary.
  `zaafpulse-gw` is a Go gateway that `zaafpulse` starts and supervises. Both ship in one archive per platform.
  Neither needs Node.js, Deno or npm packages on the machine.
- **IPC v1.** The two talk over the child's stdin and stdout with versioned messages, each described by a JSON schema
  in `ipc/v1/`. `zaafpulse doctor` shows the protocol version and the number of schemas.
- **Front mode.** With `"gateway": { "engine": "front" }` the Go gateway holds the main port and hands to the
  dashboard what it does not answer itself. The default is `"js"`: no Go process, as in v1.1.
- **Engine switches per route class.** Each gateway route class (`chat`, `chat-stream`, `messages`, `responses`,
  `gemini`, `embeddings`, `mcp`, `token-saver`, `routes` and the others) is `js` or `go` in
  `gateway.engines`, and can be compared first in shadow mode (`gateway.shadow`). Every class defaults to `js`. A class
  asked for `go` moves only after a day and 20 compared calls without a difference.
- **Egress through Go.** Outbound calls (connectors, MCP upstreams, routers, price sync, evals, remote agents,
  webhooks, second-brain sources, URL ingest, OTLP export, remote model servers) can leave through the Go gateway,
  class by class (`egress.classes`: `direct`, `check` or `go`), against an allow-list built from your own settings.
  Every class defaults to `direct`.

## What changed for you

**Smaller downloads.** One archive per platform with both programs, against the v1.1.0 download for the same
platform. The v2 figures are from the release dry run `45101126221` (packages built at `294d696`, before the version
was set to 2.0.0); the v2.0.0 archives' own sizes are those of the assets below.

| Platform | v2 archive | v1.1.0 download |
|---|---|---|
| linux-x64 | 40.2 MB | 128.3 MB |
| linux-arm64 | 39.5 MB | 124.7 MB |
| win-x64 | 37.2 MB | 95.4 MB |
| win-arm64 | 35.1 MB | 83.7 MB |

**New controls.** Governance → Compliance has twenty controls instead of eighteen:

- **Runtime permissions** shows the Deno permission set the dashboard runs under. It is `partial` on a normal
  install, because the run list holds launchers such as `osascript` and `claude` that can run any code.
- **Network egress is mediated and logged** is `off` until the Go gateway is in front, then `partial` until every
  outbound class goes through it.

**`zaafpulse doctor`** has new rows:

- `ZAAFPulse <version> (single-file build)` and `Deno <version>`;
- `Gateway (zaafpulse-gw)  <path> — found, allowed, <version>`; "not allowed" means the programs' folder is not first
  on `PATH` (start through the installer's `zaafpulse` command);
- `Gateway IPC  v1, <n> schemas`;
- `MCP clients`: clients whose registration still grants `kill` or `tasklist`; run `zaafpulse register-mcp <client>`
  for each it names;
- `MCP entries`: clients whose ZAAFPulse entry starts a program that no longer exists; run
  `zaafpulse register-mcp registered`.

**Egress defaults: `enforce` and lock-down.** With no `egress` section of your own, the allow-list enforces (a host
that no setting names is refused with `EGRESS_REFUSED`) and the network lock-down is asked for. Neither changes
anything until you move a class to `go`: with every class `direct` no call goes through Go, and the lock-down is in
force only when the gateway is in front and every egress class is on `go` and has met its gate. One exception: the Go
engine's own provider calls (route classes on `go`) are checked against the list; every configured provider's host is
on it, and a provider on `localhost`, `127.0.0.1` or `[::1]` is never checked. To turn them off, in `config.json`:

```json
{ "egress": { "allowList": "report", "lockdown": false } }
```

`"report"` records an off-list host as `would-refuse` and lets the call pass. `ZAAFPULSE_EGRESS_LOCKDOWN=0` turns the
lock-down off for one launch; `zaafpulse service install` carries it into the service file. The settings, the gate
and the classes: [docs/governance.md, Network egress settings](https://github.com/rifqifitriady/ZAAFPulse-deno-go/blob/v2.0.0/docs/governance.md#network-egress-settings).

## Platforms

Four targets:

| Archive | For |
|---|---|
| `zaafpulse-2.0.0-linux-x64.tar.gz`, `zaafpulse-2.0.0-linux-arm64.tar.gz` | Linux with glibc (Ubuntu, Debian, RHEL 8/9, Rocky, AlmaLinux, Fedora, Amazon Linux, SUSE) |
| `zaafpulse-2.0.0-win-x64.zip`, `zaafpulse-2.0.0-win-arm64.zip` | Windows 10 and 11 |

**macOS has no v2 package in v2.0.0**, on Apple silicon or Intel. `install.sh` stops on any Mac (before it changes
anything) and prints the v1.x installer, which still supports macOS:

```bash
curl -fsSL https://raw.githubusercontent.com/rifqifitriady/ZAAFPulse/main/install.sh | sh
```

On a Mac, `install.sh --rollback` and `--uninstall` still work, so a Mac that already runs a v2 build can go back.
v2 itself runs on a Mac only from source (the README's "From source": Deno 2.9 or Node 18+, and Go 1.27 to build the
gateway) or from a package you build yourself with `deno task build --package` and start unpacked
([docs/install.md, Running from an unpacked archive](https://github.com/rifqifitriady/ZAAFPulse-deno-go/blob/v2.0.0/docs/install.md#running-from-an-unpacked-archive)).
The installer does not install such a package, and no release test covers it. Alpine and other musl Linux, armv7l,
ppc64le, s390x and 32-bit Windows have no v2 build either and are pointed at the same v1.x installer.

```bash
curl -fsSL https://github.com/rifqifitriady/ZAAFPulse-deno-go/releases/download/v2.0.0/install.sh | sh
```

```powershell
& ([scriptblock]::Create((irm https://github.com/rifqifitriady/ZAAFPulse-deno-go/releases/download/v2.0.0/install.ps1))) -Version v2.0.0
```

A server (as root it becomes a systemd system service): add `sudo` and `-s -- --server` to the `sh` command. Every

## Upgrading from v1.x

Run the v2 installer with the options you installed v1.x with. It stops the v1 service, keeps the v1 install in
`<prefix>/rollback` (`<prefix>/rollback/VERSION` says `v1.1.0`), installs v2 and registers again every AI client that
holds a ZAAFPulse MCP entry, since the v1 entries start a program the upgrade moved away. The data folder is not
touched: settings, keys, history, budgets and the audit log carry over, and v1.1.0 can still read the folder after v2
has used it.

The v1 installers do not move you to v2; v1.x users are not upgraded automatically.

After the upgrade, run `zaafpulse doctor` and check the rows above. What else to expect:
[the migration note](https://github.com/rifqifitriady/ZAAFPulse-deno-go/blob/v2.0.0/docs/migration/2026-11-23-migration-note.md).

## Rolling back

```bash
curl -fsSL https://github.com/rifqifitriady/ZAAFPulse-deno-go/releases/download/v2.0.0/install.sh | sh -s -- --rollback
```

```powershell
& ([scriptblock]::Create((irm https://github.com/rifqifitriady/ZAAFPulse-deno-go/releases/download/v2.0.0/install.ps1))) -Rollback
```

This stops v2 and puts the install it replaced back in place, on the same data folder. After a rollback to v1.1,
register your AI clients again with v1's `zaafpulse register-mcp <client>`. The v1.1.x installer is the second way
back; it needs `zaafpulse service uninstall` first, and on Windows the two `.exe` files deleted from
`%LOCALAPPDATA%\ZAAFPulse\bin`
([docs/install.md, Rolling back](https://github.com/rifqifitriady/ZAAFPulse-deno-go/blob/v2.0.0/docs/install.md#rolling-back)).
On Windows neither way back to v1.1.0 is verified; see [Windows and v1.1.0](#windows-and-v110).

If you turned the Go gateway on and only want it off again, you do not need to roll back: set
`"gateway": { "engine": "js" }` and `"egress": { "lockdown": false }` and run `zaafpulse service restart`. One class
back to `js` is `"engines": { "<class>": "js" }`, picked up within a minute
([the switch runbook, Rolling back](https://github.com/rifqifitriady/ZAAFPulse-deno-go/blob/v2.0.0/docs/migration/2026-11-23-switch-runbook.md#5-rolling-back)).

## Verifying the download

Every archive, both binaries inside each, `install.sh`, `install.ps1` and `SHA256SUMS.txt` carry a build-provenance
attestation made by this repository's release workflow from the `v2.0.0` tag. The installers check the archive against
`SHA256SUMS.txt` and install nothing on a mismatch; `--verify-attestation` (`-VerifyAttestation`) also checks the
attestation.

```bash
gh release download v2.0.0 --repo rifqifitriady/ZAAFPulse-deno-go
sha256sum -c SHA256SUMS.txt                           # shasum -a 256 -c on macOS
gh attestation verify zaafpulse-2.0.0-linux-x64.tar.gz --repo rifqifitriady/ZAAFPulse-deno-go
gh release verify v2.0.0 --repo rifqifitriady/ZAAFPulse-deno-go
gh release verify-asset v2.0.0 zaafpulse-2.0.0-linux-x64.tar.gz --repo rifqifitriady/ZAAFPulse-deno-go
```

The attestation must name `.github/workflows/release.yml@refs/tags/v2.0.0`. The Windows binaries are not
code-signed: a browser download needs the SmartScreen step once
([docs/install.md, Unsigned binaries](https://github.com/rifqifitriady/ZAAFPulse-deno-go/blob/v2.0.0/docs/install.md#unsigned-binaries-first-start-and-verifying-a-download)).
The installers' own downloads are not marked.

## Verification status

**What is proven:**

- **CI on five OS and CPU combinations.** The Node suite and the Go tests run on Linux x64, macOS arm64, Windows x64
  and Windows arm64, the Deno suite on Linux and macOS. The four release packages are built and smoke-tested on
  runners of their own OS and CPU, Linux arm64 included, with the gateway in front (all four passed in the dry run
  above). The regular CI also builds and smoke-tests a darwin-arm64 package, which this release does not ship.
- **The gateway contract suite** (black-box HTTP) passes with the gateway in each mode: `js`, `front`, `go` and
  `shadow` (where any difference between the two engines fails the run).
- **The Go ports are checked against fixtures written by the real JS** code, regenerated on Node and on Deno in CI;
  a difference fails the run.
- **An independent security review** of the IPC, the Deno permission matrix, the egress proxy and provider auth found
  no critical or high findings, one medium and four low. All five are fixed, each with a test (the medium one: the Go
  egress path now refuses the cloud metadata service on every path and redirect hop). `govulncheck`, `deno audit` and
  `npm audit` found nothing else.
- **Two stream races were found and fixed.** Both cut a streamed answer after its first event when the server closed
  the request body before the gateway's proxy finished reading it: once for hand-offs and shadowed requests, once on
  the front's plain proxy. After the second fix, 0 cuts in 80,000 contract-harness streams in front mode (4 before),
  and 0 in 300,000 streamed requests through the real front.
- **M12, upgrade and rollback.** `scripts/upgrade-check.js` (v1.1.0, then v2 with the gateway in front, then v1.1.0
  again on one data folder) passed on macOS: the audit chain verified, the usage totals counted both versions' calls,
  and every `config.json` key v1 wrote was unchanged. It passed in the release workflow on linux-x64 and win-x64 too.
- **The Windows install, in the release workflow.** On Windows x64 and arm64 the release install test passed for the
  v2 clean install with `install.ps1`, the background service (the Startup launcher), `zaafpulse doctor`, the gateway
  in front (ready, at the package version) and the uninstall, which keeps the data.
- **Size (M6):** every archive is smaller than the v1.1.0 download for its platform (table above).

**What is not yet confirmed:**

- **The quiet-machine benchmarks** have not been run: M3 (gateway overhead, non-streaming), M4 (500 concurrent
  streams) and the re-recorded stream baseline. They run with `deno task bench:final` on a quiet machine and are
  published after this release
  ([docs/migration/final-benchmarks.md](https://github.com/rifqifitriady/ZAAFPulse-deno-go/blob/v2.0.0/docs/migration/final-benchmarks.md)).
  An earlier run on the private tier, on a laptop with other apps open, met the M3 and M4 targets; it is not
  quiet-confirmed, and the external tier, the translated `/v1/messages` path and the token saver have not been
  measured that way yet.
- **`install.ps1` and the Windows install paths** ran for the first time in this release's workflow, so they have no
  history of earlier runs. The release dry runs found and fixed three faults in the new Windows installer before this
  release: it waited forever after "ZAAFPulse is running" (the background server held its output open), its uninstall
  in Windows PowerShell 5.1 ended with an error when no `-System` task existed, and it relied on a PowerShell module
  that is not loaded when Windows PowerShell is started from PowerShell 7. v1.x never had these steps in this form.
- **Upgrading an installer-made v1.1.0 install on Windows, and `-Rollback` to it, are not verified.** The release
  install test cannot make a v1.1.0 install to start from, because v1.1.0's own Windows installer cannot install
  v1.1.0 from GitHub ([Windows and v1.1.0](#windows-and-v110)); that part of the Windows test is skipped. On Linux the
  upgrade from v1.1.0 and `--rollback` are part of the release install test.
- **The macOS launchd install path is not verified.** No macOS package ships, so no release install test covers it.
- **Live provider authentication** was not exercised against real services: Azure OpenAI with Entra ID, Vertex AI
  with a service account, a refresh-token provider and an Anthropic-format provider behind OAuth2. These are covered
  by tests against local fakes only.

## Windows and v1.1.0

The v1.1.0 Windows installer (`install.ps1` at tag `v1.1.0` of rifqifitriady/ZAAFPulse) stops before it installs
anything, in every setup the release tests tried:

- **PowerShell 7:** it reads `SHA256SUMS.txt` with `Invoke-WebRequest`, whose `.Content` is bytes for a release asset
  (served as `application/octet-stream`), finds no checksum line, and stops with "Could not get a verified package for
  v1.1.0 (SHA256SUMS.txt missing or unreachable)".
- **Windows PowerShell 5.1 with `node` on PATH:** its Node.js version check, `node -p
  'process.versions.node.split(".")[0]'`, loses the double quotes on the way to `node` (Windows PowerShell 5.1 passes
  them unescaped), so `node` reports a syntax error and the installer stops.
- **Windows PowerShell 5.1 without `node` on PATH:** it downloads Node.js, then stops at the same checksum step as in
  PowerShell 7.

What this means on Windows:

- A v1.x install made earlier keeps working. If you need v1.x, keep that install: reinstalling v1.1.0 with its own
  installer does not work.
- Upgrading such an install to v2 and `-Rollback` back to it are expected to work as on Linux, but are not verified on
  Windows.
- To go back from the Go gateway, stay on v2 and use the switch runbook's rollback: `"gateway": { "engine": "js" }`
  (and `"egress": { "lockdown": false }`) in `config.json`, then `zaafpulse service restart`
  ([the switch runbook, Rolling back](https://github.com/rifqifitriady/ZAAFPulse-deno-go/blob/v2.0.0/docs/migration/2026-11-23-switch-runbook.md#5-rolling-back)).
  This is the recommended way back on Windows, rather than reinstalling v1.1.0.

## Known differences from v1.x

- The installers and releases come from this repository, not from `raw.githubusercontent.com/rifqifitriady/ZAAFPulse`.
  `install.sh` has no `--source` or `--version main`: v2 installs releases only.
- `--uninstall` keeps your data (v1 deleted the Linux data folder inside the install folder); `--purge` deletes it.
- The dashboard runs inside a Deno permission set: it may write only the data folder, the temp folder, the skill
  folders and the AI clients' config folders, and run only a listed set of programs. A program outside the list (a
  Claude Code installed only inside an IDE extension folder, a model server that is not a preset) is refused with
  "Requires ... access to ...". On Linux, pausing and stopping agents needs `ps` and `lsof` installed.
- A request whose target is in absolute form (`GET http://host/path HTTP/1.1`) is refused with 400.
- URLs given to the RAG service are refused for a wider set of private addresses (among them IPv4-compatible IPv6,
  NAT64's local-use range, site-local `fec0::/10`, Teredo and 6to4 addresses that embed a private IPv4 address).
- The Docker image still runs on Node.js.

Once you put the Go gateway in front, more differences apply (budgets checked from a snapshot sent every second,
gzip-only outbound requests through Go, a 16 MiB limit on one stream event, credential headers dropped on a
cross-origin redirect, among others). They are listed in
[the migration note](https://github.com/rifqifitriady/ZAAFPulse-deno-go/blob/v2.0.0/docs/migration/2026-11-23-migration-note.md#differences-you-may-notice-once-the-go-gateway-is-in-front).
